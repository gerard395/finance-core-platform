# W1-003A – Dashboard Read Infrastructure Design

## Status and retained W1-004 findings

**Design complete; no production implementation in this story.** W1-004 remains blocked pending W1-003B through W1-003E.

The W1-004 inventory established that Reporting already owns the required arithmetic, but accepts only in-memory inputs. There are no persistence tables, Application read contracts or Infrastructure adapters for `LedgerAccount`, `JournalEntry`/`JournalEntryLine`, `OpenItem`/`OpenItemSettlement`, `TaxPosting`, or `Relation`/`Customer`/`Supplier`. Consequently, tenant-scoped reads cannot yet be enforced. In addition, `OpenItem` exposes only `RelationId`; no persisted source can currently identify that Relation as Customer or Supplier. These are the consolidated blockers this design resolves.

## Read architecture and invariants

```text
Presentation
    ↓
Application use case → Application read contracts
                              ↓
                    Infrastructure adapters
                              ↓
                           database

Application supplies reconstituted inputs → Domain Reporting
                                            ├─ TrialBalance → ProfitAndLoss
                                            ├─ OpenItemsReport
                                            └─ VatOverview
```

- Presentation never queries Eloquent and receives only a typed Application result.
- Application orchestrates reads and the existing Reporting objects; it does not duplicate Trial Balance, Profit & Loss, historical OpenItem or VAT arithmetic.
- Reporting remains framework- and database-independent.
- Every financial/classification read requires `AdministrationId`. Inclusive period or as-of filters are also mandatory where meaningful.
- Infrastructure applies Administration, status and date predicates before hydration and loads only relevant children. SQL may select/filter but must not become an alternative financial-calculation source.
- Money is stored as an exact decimal plus three-letter Currency, never as float. Computed balances, status, revenue and VAT position are not stored.
- Foreign keys enforce local referential integrity. Cross-capability write orchestration remains in Application; no aggregate mutates another aggregate.

## W1-003B – Accounting Read Persistence

### Tables and constraints

`ledger_accounts`:

- UUID `id` primary key; UUID `administration_id` foreign key to Administrations.
- Existing factual fields: code, name, `LedgerAccountType`, `LedgerAccountStatus`.
- Unique `(administration_id, code)`; index `(administration_id, type)`.
- Creation/update audit timestamps for mutable master data.

`journal_entries`:

- UUID `id` primary key; UUID `administration_id` foreign key; UUID `journal_id` as the existing Domain reference.
- Posting date, reference and `JournalEntryStatus`.
- Index `(administration_id, status, posting_date)` for posted period reads; index/constraint on journal reference is not invented because the Domain does not define its uniqueness.
- Creation timestamp and a posting/audit timestamp if supplied by the write workflow. Posted rows are immutable; database/application guards must reject updates to posted financial facts. No artificial business timestamp is reconstructed into Domain.

`journal_entry_lines`:

- UUID `id` primary key; UUID `journal_entry_id` foreign key; UUID `ledger_account_id` foreign key.
- Exact nullable debit amount, exact nullable credit amount, three-letter Currency, and description. Description is additionally required by the factual `JournalEntryLine` constructor.
- Exactly one of debit/credit must be non-null; amounts must be non-negative. An entry's line order has no business meaning, but reads use stable ID order.
- Creation audit timestamp; lines belonging to a posted entry are immutable.

No Journal table is required by the dashboard read itself. `journal_id` remains a durable UUID reference; adding Journal master-data persistence belongs in W1-003B only if the write-side foreign-key requirement makes it necessary, and must use the factual `Journal` fields rather than a stub record.

### Explicit tenant ownership decision

`LedgerAccount` and `Journal` currently contain no `AdministrationId`. Ownership must therefore not be inferred from entry usage or globally unique UUIDs. W1-003B records `administration_id` explicitly as persistence ownership metadata and its save/read contracts receive that ID explicitly. Hydration reconstructs the unchanged Domain entity, while the adapter enforces the row's tenant scope. A future Domain change may make ownership intrinsic, but is not required or silently implied by this read foundation.

Every loaded entry line's account must exist in the same Administration. Because the current entity cannot validate that external fact, W1-003B must enforce it through tenant-scoped adapter queries and database-safe composite ownership constraints where supported. Failure to implement this explicit cross-row tenant constraint is a blocker for W1-003B.

### Contracts, adapter and hydration

- `LedgerAccountReadRepository::forAdministration(AdministrationId): list<LedgerAccount>`.
- `JournalEntryReadRepository::postedForPeriod(AdministrationId, PostingDate from, PostingDate to, Currency): list<JournalEntry>`.
- Narrow write persistence needed to create the read source may accompany W1-003B, but must remain separate from the read interface and preserve PostingEngine exclusivity.
- Eloquent adapters query by Administration first, then status/date/currency, eager-load only matching lines, and fail closed on malformed or cross-tenant data.
- Reconstitution uses the factual constructors/value objects. For each entry: instantiate with stored status context in a safe sequence, add every stored line through `addLine`, and call `post()` only when the stored status is Posted. No reflection or public setters are introduced. Draft reads are outside the dashboard contract.

### Tests

Roundtrips for all factual fields; Posted-only inclusive period filtering; tenant A/B isolation; exact decimal/currency preservation; debit/credit check constraints; account and child foreign keys; posted-row immutability; cross-tenant account rejection; deterministic complete line hydration; no Laravel dependency under Domain. Run Integration explicitly.

## W1-003C – Open Item Read Persistence

### Tables and constraints

`open_items`:

- UUID `id` primary key; UUID `administration_id` foreign key; UUID `relation_id`; UUID `journal_entry_id` foreign key.
- Exact positive original amount, Currency and opening date.
- Index `(administration_id, opened_on)` and tenant-scoped relation index.
- Creation audit timestamp. Immutable opening context; do not persist open amount or status.

`open_item_settlements`:

- UUID `id` primary key; UUID `open_item_id` foreign key; effective date; exact positive amount and Currency; UUID source JournalEntry foreign key; `Applied`/`Reversal` type; nullable UUID `reversed_settlement_id` self-reference.
- Applied requires no reversal reference; Reversal requires one applied settlement belonging to the same OpenItem. One reversal per applied settlement is database-safe through a unique nullable reversal reference plus adapter validation.
- Append-only creation timestamp. No update/delete path for settlement facts; corrections are new Reversal rows.
- Index `(open_item_id, effective_date, id)` supports deterministic historical hydration.

The open-item Relation foreign key becomes enforceable once W1-003E supplies tenant-owned Relations. Until then W1-003C must at least retain the immutable `RelationId` and reject any available cross-tenant mismatch; it does not classify the item.

### Contract, adapter and hydration

- `OpenItemReadRepository::asOf(AdministrationId, PostingDate, Currency): list<OpenItem>`.
- Adapter filters `administration_id` and `opened_on <= asOf`, then loads the complete settlement history required to calculate state at that date. It may omit settlements after the requested as-of only if doing so still reconstructs a valid historical aggregate; the conservative v1 design loads complete history for the selected tenant/items and lets `OpenItemsReport` apply the as-of truth.
- Reconstruct the base `OpenItem`, then replay immutable settlements through `applySettlement()` and `reverseSettlement()` in valid deterministic dependency order using stored identifiers, dates, amounts and source JournalEntry IDs. Never assign settlements or derived state directly.

### Tests

Base and complete-history roundtrip; Applied/Reversal replay; append-only enforcement; reversal uniqueness/reference integrity; source JournalEntry and OpenItem foreign keys; same-currency constraints; tenant A/B isolation; inclusive as-of selection and historical amounts; no stored derived status/open amount; no Domain-to-Laravel dependency. Run Integration explicitly.

## W1-003D – Fiscal TaxPosting Read Persistence

### Table and constraints

`tax_postings`:

- UUID `id` primary key, providing database-safe global `TaxPostingId` uniqueness.
- UUID `administration_id` foreign key; UUID `tax_code_id`; exact TaxRate snapshot; exact taxable-base and tax amounts with their unambiguous three-letter Currency.
- Direction, `Original`/`Reversal` type, source document type/id/line ID, posting date, JournalEntry ID, base JournalEntryLine ID, nullable tax JournalEntryLine ID, nullable reversed TaxPosting ID.
- Self foreign key for reversal; Original requires null reversed ID, Reversal requires non-null. Unique nullable `reversed_tax_posting_id` prevents multiple reversals of one Original; adapter validates same Administration, Original target and unchanged direction.
- Index `(administration_id, posting_date)` and, where useful, `(administration_id, direction, posting_date)`.
- Append-only creation timestamp. No mutation/deletion of fiscal facts; fixes are Reversal facts. No persisted VAT totals.

Journal/line references must point to the same Administration through explicit composite ownership constraints or transactional adapter validation; raw globally unique IDs are not sufficient tenant proof.

### Contract, adapter and hydration

- `TaxPostingReadRepository::forPeriod(AdministrationId, DateTimeImmutable start, DateTimeImmutable end, Currency): list<TaxPosting>`.
- Adapter applies tenant, inclusive period and currency filters before constructing each immutable `TaxPosting` from every stored snapshot/audit field.
- Persistence performs selection and identity/reference enforcement only. `VatOverview` remains the sole VAT aggregation and Original/Reversal arithmetic source.

### Tests

Original and Reversal roundtrips including 0%/null tax-line semantics; exact rate and Money snapshots; tenant A/B and inclusive period filters; primary/foreign/self-reference constraints; one reversal per original; cross-tenant reference rejection; append-only behavior; no VAT calculation in adapter; no Domain-to-Laravel dependency. Run Integration explicitly.

## W1-003E – Relation Classification Read Persistence

### Factual classification decision

`Relation`, `Customer` and `Supplier` are separate entities with separate immutable IDs. Customer and Supplier each reference a `RelationId`; neither constructor excludes the other. Therefore one Relation may explicitly be Customer, Supplier, both, or neither. Active status is part of each classification, but classification truth must not be inferred from amount sign, ledger account, source document type or ID format.

Like LedgerAccount, these entities currently carry no `AdministrationId`. W1-003E makes tenant ownership explicit in persistence and in every Application contract. No global Relation lookup is allowed.

### Tables and constraints

`relations`:

- UUID `id` primary key; UUID `administration_id` foreign key; factual Relation code, display name and active state.
- Unique `(administration_id, code)` and tenant lookup index; creation/update audit timestamps.
- Dashboard classification does not require Contact, Address or BankAccount child persistence; those remain outside this focused story unless an existing write requirement separately mandates them.

`customers` and `suppliers`:

- Separate UUID primary key, UUID `administration_id`, UUID `relation_id`, factual Customer/Supplier number and active state.
- Foreign key/composite ownership ensures the Relation belongs to the same Administration.
- Unique `(administration_id, relation_id)` per classification and unique `(administration_id, customer_number)` / `(administration_id, supplier_number)`.
- Creation/update audit timestamps. No exclusivity constraint between Customer and Supplier rows, deliberately allowing both.

### Contract, adapter and OpenItem join

- A focused `RelationClassificationReader` accepts `AdministrationId` plus the requested RelationIds and returns typed classifications (`isCustomer`, `isSupplier`) for exactly those IDs. Missing rows mean neither; inactive semantics must be specified by the consuming use case rather than silently filtered. For the dashboard, classification of the financial fact should remain explicit and stable; W1-003E tests and documents whether inactive classifications still classify historical OpenItems before W1-004 resumes.
- Adapter queries only requested IDs within the Administration and performs set-based joins; it never reads tenant-wide Relations unnecessarily.
- W1-004 groups `OpenItemsReport` lines by their `RelationId` and consults this explicit result. If a Relation is both, the same OpenItem cannot be assigned reliably to receivables versus payables from Relation classification alone. W1-003E must therefore establish an explicit per-OpenItem business-side discriminator or another authoritative linkage before W1-004. It may not use heuristics.

### Newly identified blocker

The existing Domain permits Customer/Supplier overlap, while `OpenItem` has only `RelationId`. For a dual-classified Relation, classification alone is ambiguous. W1-003E is blocked from declaring the dashboard classification complete until an explicit business decision identifies the receivable/payable side on the OpenItem or via an authoritative immutable source linkage. This decision may require a small Domain design story/ADR before or as the first step of W1-003E; persistence must not guess.

### Tests

Relation, Customer and Supplier roundtrips; tenant ownership and composite foreign keys; per-tenant code/number/classification uniqueness; Customer-only, Supplier-only, both and neither; active/inactive historical semantics; batch lookup restricted to requested IDs; cross-tenant Relation rejection; explicit ambiguity handling for dual classification; no heuristic and no Domain-to-Laravel dependency. Run Integration explicitly.

## W1-004 flow after implementation

```text
validated active Administration
    ↓
GetDashboardOverview(AdministrationId, periodStart, periodEnd, Currency)
    ↓
tenant-scoped read contracts
    ↓
TrialBalance → ProfitAndLoss.totalRevenue
OpenItemsReport + explicit receivable/payable classification
VatOverview.netVatPosition
    ↓
typed DashboardOverviewResult
    ↓
server-side Money formatter → Blade
```

The current calendar month is selected in configurable Application/server time context. The use case returns AdministrationId, inclusive period boundaries, Currency and four `Money` values. Empty sources yield four Money zeros. Presentation formats only and never receives collections to aggregate.
