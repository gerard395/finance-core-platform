# W4-008 – Sales Invoice Posting Web Action

## Route and authorization

W4-008 adds exactly one mutation endpoint:

`POST /sales/invoices/{invoice}/post` (`sales.invoices.post`)

It runs through the existing `web` middleware group (including Laravel CSRF protection), then `auth`, `domain.active`, `administration.active`, and `EnsureSalesPermission::using(SalesPermission::PostInvoices)`. There is no GET mutation and no Paid route.

`PostInvoices` is the only posting permission. It does not imply or require View, ManageInvoiceDrafts or IssueInvoices. A `SALES_POSTER` can therefore submit a valid direct POST without View and is redirected to `/app`. Permissions remain Administration-scoped and revocation is effective on the next request.

## Controller and tenant boundary

`SalesInvoicePostingController` is a thin invokable action. It parses the URL UUID, obtains `AdministrationId` only from `ActiveAdministrationContext`, and invokes `PostSalesInvoice(AdministrationId, SalesInvoiceId)`. A submitted `administration_id` is ignored. Malformed identifiers and typed NotFound—including cross-tenant invoices—produce the same 404.

The controller contains no Eloquent, configuration reader, financial store, account lookup, PostingEngine or calculation. W4-007 remains the sole transaction and financial orchestration owner. Financial inconsistency is logged server-side with Administration/invoice context and never repaired by Presentation.

## Detail action and redirects

The responsive actions area shows the real button **Factuur boeken** only when the detail status is Finalized and the current Administration context grants `PostInvoices`. The form uses POST, `@csrf`, a semantic keyboard-usable button, visible focus styling and fixed server-owned text. It is hidden for Draft, Posted, Paid and Cancelled. UI visibility is only UX; route middleware and the use case remain authoritative.

Users with View return to the invoice detail. Mutation-only users without View return to `/app`. Result mapping uses only fixed messages:

- Success: `Factuur is geboekt.`
- AlreadyPosted: `Deze factuur is al geboekt.`
- ConfigurationMissing: neutral incomplete-configuration error
- ConfigurationInvalid: neutral invalid/unavailable-configuration error
- InvalidState: neutral current-status error
- FinancialStateInconsistent: neutral control-required error plus server log
- PostingFailure: neutral retry-later error
- NotFound: 404

After Success the detail displays the existing status label **Geboekt** and no longer renders the posting button. A repeated POST maps to AlreadyPosted and leaves JournalEntry, TaxPosting, OpenItem and linkage counts unchanged.

## Security and exclusions

Snapshots remain Blade-escaped and all new flash text is fixed server-side content. Presentation neither exposes Journal/LedgerAccount identities nor tries to infer readiness. Feature coverage includes least privilege, Poster-without-View, tenant isolation, fake body tenant input, malformed UUID, revocation, POST/CSRF route metadata, lifecycle visibility, safe typed errors and idempotency.

This story adds no Paid action/button, settlement, payment/bank flow, PDF/e-mail, Order conversion/allocation, credit-invoice posting or new Accounting/Fiscal/OpenItem logic.
