# W1-002 – Administration Access & Active Administration

## Status en inventarisatie

**Status:** Implemented

`AdministrationMembership` contains immutable UserId/AdministrationId, active state and an inclusive validity period. `Administration` exposes active/inactive status. Application already provides Administration and membership repositories plus a tenant-scoped effective-permission reader. W1-001D supplies authenticated Domain User resolution per request. No direct Eloquent authorization was needed.

## Webmodel

The server-side session key is `active_administration_id`. It is only a selection hint and is revalidated on every `/app` request. `EnsureActiveAdministration` parses the UUID, loads Administration and membership through Application contracts, verifies both are currently active/valid and removes stale or malformed context before redirecting to selection.

`ActiveAdministrationContext` is immutable and exists only as the current Request attribute `administration_context`. It contains the Domain User, active Administration and freshly loaded effective PermissionIds. It is neither static nor cached between requests. Membership access and action permission remain separate concerns.

## Routes and behavior

- `GET /administrations/select`: shows only currently accessible active Administrations.
- `POST /administrations/select`: validates the requested UUID and access before writing session state, then redirects to the named `/app` route.
- The same POST handles first selection and switching; there is no weaker switch path or user-controlled redirect.
- `/app` requires `auth`, `domain.active` and `administration.active` in that order.
- Missing, malformed, revoked or inactive context is cleared and redirected safely to selection. A failed switch leaves the prior valid session selection unchanged and reveals no tenant details.
- Logout invalidates the complete session, therefore also removes `active_administration_id`.

## UI and security

The responsive Blade/Tailwind selection page shows user identity, accessible Administration cards, CSRF-protected selection buttons and POST logout. The placeholder shows only user name, active Administration name, count of request-scoped effective permissions, switch action and logout—no financial data.

Backend checks run on every scoped request. Request IDs and hidden navigation are never authorization evidence. Invalid/unauthorized selections use one generic validation message. API-specific error behavior remains future scope.

## Tests and debt

Feature tests cover visibility, valid/invalid/unauthorized selection, session integrity, scoped access, malformed context, revocation, inactive Administration, switching and logout cleanup using real persistence adapters. Existing W1-001B Integration tests prove effective permissions are distinct and isolated by User plus Administration. `phpunit.xml` still omits Integration discovery; explicit Integration execution remains required until W1-005.
