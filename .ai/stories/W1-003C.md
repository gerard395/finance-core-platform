# W1-003C – Open Item Read Persistence

## Status and source truth

**Implemented.** The earlier run stopped because settlement history could only be restored by replaying business commands. W1-003C0 supplied `OpenItem::reconstitute(...)`, which restores immutable basis context and complete validated history at once without `applySettlement()`, `reverseSettlement()`, events, reflection or setters.

Persistence contains only factual source truth: OpenItem ID, Administration, Relation reference, originating JournalEntry, exact original Money/Currency and opening date; settlements contain their ID, owning OpenItem/Administration, effective date, exact Money/Currency, source JournalEntry, Applied/Reversal type and optional reversed settlement ID. Open amount and status are absent from the schema and remain Domain derivations.

## Schema, Money and tenant integrity

Two ordered reversible migrations add `open_items` and `open_item_settlements`. Both use UUID primary identities, explicit Administration context and timestamps. Amounts use the W1-003B exact text-string pattern plus `CHAR(3)` Currency, with no FLOAT, DOUBLE or PHP float conversion; eight decimal places roundtrip unchanged.

Tenant-bearing composite foreign keys guarantee:

- an OpenItem source JournalEntry belongs to the same Administration;
- a settlement belongs to an OpenItem in that Administration;
- a settlement source JournalEntry belongs to that Administration;
- a Reversal references a settlement in that Administration.

Primary/unique constraints reject duplicate IDs; a nullable tenant/reversed-ID unique constraint permits at most one Reversal per Applied fact. Every financial foreign key restricts deletion. RelationId is deliberately stored without a fake FK because Relations persistence follows in W1-003E; it carries no Customer, Supplier, receivable or payable meaning here.

## Application contracts and append-only writes

The narrow contracts are:

- `OpenItemReadRepository::findForAdministrationAsOf(AdministrationId, PostingDate)`;
- `OpenItemStore::append(OpenItem)` for one new settlement-free basis fact;
- `OpenItemSettlementStore::appendSettlement(OpenItem, OpenItemSettlement)` for exactly one new Domain-owned child fact.

`EloquentOpenItemRepository` implements all three and is bound in `AppServiceProvider`. It exposes no save, upsert, update or delete API. Basis append requires a new ID and a Posted same-tenant source JournalEntry. Settlement append requires the exact child owned by the supplied valid aggregate, locks the persisted OpenItem, verifies persisted history exactly precedes that one candidate, verifies a Posted same-tenant source entry, and inserts only the new row transactionally. Existing basis or settlement facts are never rewritten; Reversal preserves Applied.

## Read and hydration strategy

The read query requires Administration and as-of date and selects only `opened_on <= asOf`, ordered by opening date then OpenItem ID. It intentionally loads the complete ordered settlement history for every selected item, including facts after the requested date. This preserves the full audit trail; `openAmountAt()` and `statusAt()` remain the only historical filter/arithmetic source.

Infrastructure maps exact row strings and UUIDs to typed `OpenItemSettlement` entities, then calls only `OpenItem::reconstitute(...)`. It performs no settlement or Reporting arithmetic. The resulting aggregates feed `OpenItemsReport` directly and produce identical historical results.

## Verification coverage

Infrastructure integration tests prove exact basis and eight-decimal Money roundtrip, RelationId without FK, Applied/Reversal fields and ordering, future-history hydration with historical as-of outcomes, append-only preservation, A/B read isolation, adapter-level and database-level cross-tenant rejection, duplicate identity rejection, missing update/delete contracts, derived-state column absence, and direct `OpenItemsReport` compatibility. `RefreshDatabase` validates fresh schema creation and all foreign/self-reference constraints.

No TaxPosting persistence, Relations persistence, classification, dashboard or Presentation code is included.
