# W1-003E0 – OpenItem Receivable/Payable Classification Contract

## Decision and factual inventory

Accounting now owns the required immutable `OpenItemType` with exactly `Receivable` and `Payable`. Receivable means an amount the Administration is owed by the counterparty; Payable means an amount the Administration owes the counterparty. `RelationId` answers who the counterparty is, while `OpenItemType` answers the financial nature of the open item. These concepts are independent and no Customer/Supplier, amount, account, JournalEntry or ID heuristic is used.

`OpenItem` previously accepted OpenItem, Administration, Relation and source JournalEntry identities, original Money and opening PostingDate. Its reconstitution factory accepted the same basis plus complete settlement history. Both APIs now require `OpenItemType` immediately after `JournalEntryId`, and `type()` exposes it without a mutation API. Settlement validation, ordering, open-amount and status derivation are unchanged.

The complete caller inventory was:

- `EloquentOpenItemRepository::hydrate()`;
- `OpenItemTest` constructor and reconstitution fixtures;
- `OpenItemsReportTest` fixtures;
- `EloquentOpenItemReadPersistenceTest` fixtures and cross-tenant case;
- `EndToEndFinancialFlowTest` Sales invoice flow and its settlement fixtures.

No Application production service currently constructs an OpenItem. The existing end-to-end flow is explicitly Sales/Customer-origin and now supplies Receivable. There is no existing Purchasing OpenItem integration flow to migrate. SalesCreditInvoice and PurchaseCreditInvoice retain CustomerId/SupplierId context but do not currently create OpenItems, so this story introduces no new credit-note lifecycle rule. A future Sales-origin credit flow remains on the Receivable side and a Purchasing-origin flow on the Payable side, with its actual open-item behavior requiring its own explicit lifecycle design.

## Persistence and hydration

The mandatory database precondition was checked before changes: Sail and healthy MySQL were running and `open_items` contained exactly **0 records**. Migration `000015` can therefore add required `open_item_type` without a default or fabricated backfill. The database enum admits only `receivable` and `payable`; the column is non-null and has no default. The migration is reversible.

`EloquentOpenItemRepository::append()` writes `$openItem->type()->value`. Hydration uses `OpenItemType::from()` and passes the exact stored value to `OpenItem::reconstitute()`. Infrastructure performs no inference. `OpenItemRecord` exposes the field only for persistence. The existing `OpenItemReadRepository` remains unchanged because its returned Domain objects now carry the typed truth.

Integration coverage verifies both types, exact stored/hydrated values, required/invalid database rejection, settlement-history preservation, as-of reads and unchanged tenant isolation. Reporting arithmetic is unchanged; W1-004 can later split tenant-scoped OpenItems by `OpenItem::type()` before calculating receivable/payable presentation values.

## Architecture

Accounting has no Sales, Purchasing, Customer, Supplier, Reporting, Laravel or persistence dependency. Sales/Purchasing Domain received no Accounting dependency. Explicit source context is supplied at the caller boundary, persistence merely stores it, and Reporting does not infer it. The Accounting README records the invariant.
