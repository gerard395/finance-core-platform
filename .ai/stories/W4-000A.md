| Role | Stable RoleId | Exacte permissions |
| --- | --- | --- |
| `SALES_VIEWER` / Sales Viewer | `69a2fd6d-3660-47a5-a5da-e902a6313acf` | View |
| `SALES_EDITOR` / Sales Editor | `daf61074-ae86-4f87-ab50-9d2afaec3281` | View, Manage Quotations, Manage Orders, beide Draft Manage |
| `SALES_MANAGER` / Sales Manager | `bd2b8676-25bc-4399-bb7b-966ed32aeb36` | Alle Editor-rechten plus beide Issue-rechten |
| `SALES_POSTER` / Sales Poster | `3496dda5-7528-4c2a-8dfa-e97751536f6e` | Uitsluitend beide Post-rechten |

Editor kan niet Issue/Post. Manager kan Issue maar niet Post. Poster kan Post en krijgt niet automatisch View, Draft of Issue. Invoice Post en CreditInvoice Post/reversal blijven afzonderlijke permissions; autorisatie controleert nooit een rolnaam. Memberships kunnen rollen expliciet combineren.

## Provisioning en database

`SalesAuthorizationProvisioner` gebruikt bestaande Identity-repositories binnen één `TransactionManager`-boundary. Hij creëert of normaliseert negen permissions, vier rollen en vijftien exacte role-permissionmappings. Alle definition- en assignment-UUID's zijn eenmaal centraal vastgelegd. Een tweede run behoudt identities en aantallen, activeert bekende definitions/mappings en laat unrelated Identity-data ongemoeid.

Een bestaand record met alleen dezelfde identity of alleen dezelfde canonical code is ambigu en wordt geweigerd. Een stable assignment-id die bij een ander paar hoort wordt eveneens geweigerd. De transactie voorkomt gedeeltelijke provisioning. De bestaande UUID-primary keys, unieke codes en unieke role/permissioncombinatie zijn voldoende; er is geen migration.

`SalesAuthorizationSeeder` is reproduceerbaar en wordt na de Relations-seeder door `DatabaseSeeder` aangeroepen. Er wordt geen Role aan User, AdministrationMembership of demo-account toegewezen.

## Request-scoped authorization en tenantisolatie

`EnsureSalesPermission::using(SalesPermission::...)` volgt het bestaande middlewarepad:

```text
auth
→ active Domain User
→ active Administration
→ actuele effectieve PermissionIds uit User + AdministrationMembership + roles
→ vereiste stable Sales PermissionId
→ allow of HTTP 403
```

Het middleware gebruikt `ActiveAdministrationContext` en `PermissionAuthorizer`, queryt geen database en faalt gesloten bij ontbrekende context of onbekende code. Effectieve permissions worden voor iedere request vanuit de actieve Administration opgelost. Een role in Administration A geldt niet in B; revocation werkt bij de volgende request en een inactive membership wordt vóór Sales-autorisatie afgewezen.

## Toekomstige routemapping

| W4-handeling | Typed permission |
| --- | --- |
| Alle Sales list/detail/read | `SalesPermission::View` |
| Quotation writes en geldige lifecycle | `SalesPermission::ManageQuotations` |
| Order writes en geldige lifecycle | `SalesPermission::ManageOrders` |
| Invoice Draft create/edit/lines | `SalesPermission::ManageInvoiceDrafts` |
| Invoice finalize/issue | `SalesPermission::IssueInvoices` |
| Invoice financiële/fiscale posting | `SalesPermission::PostInvoices` |
| Creditinvoice Draft create/edit/lines | `SalesPermission::ManageCreditInvoiceDrafts` |
| Creditinvoice finalize/issue | `SalesPermission::IssueCreditInvoices` |
| Creditinvoice posting plus gekoppelde reversal | `SalesPermission::PostCreditInvoices` |

De toekomstige sidebar “Verkoop” toont Offertes, Orders, Facturen en Creditfacturen uitsluitend als de echte route bestaat en `SalesPermission::View` is toegestaan. Navigationvisibility is geen securitygrens. W4-000A activeert geen Sales-route of placeholder.
