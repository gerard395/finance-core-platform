# W4-007A0 – Sales Posting Configuration & Source Linkage

## Inventory and decision

- W4-007A00 supplies Administration-owned Journal persistence, tenant-scoped reads, global `JournalId`, composite `(administration_id, id)` ownership and the JournalEntry same-tenant FK.
- LedgerAccounts are durable Administration-owned masterdata with global identity, composite ownership, active/inactive status and tenant-scoped reads.
- SalesInvoices persist global `SalesInvoiceId` plus `AdministrationId` and expose composite ownership.
- JournalEntries, TaxPostings and OpenItems already expose composite Administration ownership. OpenItems reference their source JournalEntry.
- `CreateSalesInvoicePostingRequest` uses one revenue account. `PostSalesInvoiceWithTax` accepts revenue/VAT IDs per fiscal line but does not require different accounts. V1 therefore supplies one configured revenue account and one configured output-VAT account to every line; no mapping is inferred.
- TaxPostings already store immutable `sales_invoice` source-document identity, source-line identity and JournalEntry/line identities. No extra TaxPosting join table is required.

Before migration, the development database contained neither target table nor conflicting configuration/linkage persistence. It contained zero SalesInvoices, JournalEntries and OpenItems, so no backfill or conversion was required.

## Configuration ownership and readiness

`sales_posting_configurations` has exactly one mutable setup row per Administration and explicitly maps:

1. Sales Journal → `JournalId`
2. Accounts receivable → `LedgerAccountId`
3. Revenue → `LedgerAccountId`
4. Output VAT → `LedgerAccountId`

All references are composite same-tenant foreign keys with restrictive deletes. The reader/store require an active Sales-type Journal and active LedgerAccounts. Account business roles come solely from their explicit slots; account number, name, type, ordering and other heuristics are never used.

`SalesPostingConfigurationReader` returns typed `Success`, `Missing` or `InvalidReference`. `SalesPostingConfigurationStore` is a narrow validated save contract with no delete API. Upsert is safe because configuration is intentionally one mutable settings row per Administration. No production defaults are provisioned, so an unconfigured development Administration remains `Missing`.

## Append-only source linkage

`sales_invoice_postings` is the authoritative SalesInvoice → JournalEntry and SalesInvoice → OpenItem audit linkage. It stores no amounts. Its composite primary key `(administration_id, sales_invoice_id)` is the database idempotency boundary; tenant-unique JournalEntry and OpenItem references prevent reuse across invoice postings. All three source references use same-tenant composite foreign keys and restrictive deletes.

`SalesInvoicePostingRepository` exposes only tenant-scoped `findForInvoice` and `append`. Duplicate attempts return typed `AlreadyExists`; no update, delete or upsert exists and duplicate SQL details are not exposed. The adapter uses the ambient database connection and creates no autonomous transaction, so a future W4-007 outer transaction can atomically persist financial facts and linkage; rollback removes the append.

TaxPosting traceability remains authoritative through immutable `TaxSourceDocumentType::SalesInvoice`, invoice UUID, line UUID and JournalEntry identities. JournalEntry itself needs no Sales dependency. OpenItem already records its JournalEntry source, while this mapping makes the exact invoice relationship explicit.

## Concurrency and security

The primary key is the hard winner boundary for competing appends. The adapter performs a friendly precheck and, on a unique race, rereads the winner and returns `AlreadyExists` without overwriting or leaking SQL. Tests cover durable single-winner behavior, tenant isolation, database-level cross-tenant rejection, restrictive deletion, invalid/inactive configuration, append-only surface and outer rollback.
