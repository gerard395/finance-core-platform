# W2-000A – Relations Permission Contracts

## Feitelijke basis

W2-000A0 definieert en provisiont vijf bestaande Relations-businesspermissions als stable Identity-definities: `RELATIONS.VIEW`, `RELATIONS.CREATE`, `RELATIONS.UPDATE`, `RELATIONS.CLASSIFY_CUSTOMER` en `RELATIONS.CLASSIFY_SUPPLIER`. Hun vaste `PermissionId`s zijn in iedere omgeving gelijk. De capabilityrollen Viewer, Editor en Manager koppelen deze permissions system-wide; een role geldt voor een gebruiker uitsluitend via een actuele, actieve `MembershipRole` van een geldige `AdministrationMembership`.

`EloquentAuthorizationReadRepository::effectivePermissionIds()` selecteert per UserId, AdministrationId en requestmoment alleen permissions via een geldige actieve membership, actieve membership-role, actieve role, actieve role-permission en actieve permission. `AdministrationAccessResolver` voert deze query bij iedere administration-scoped request opnieuw uit. `ActiveAdministrationContext` bevat daardoor een request-scoped Domain User, actieve Administration en actuele `list<PermissionId>`; er bestaat geen globale of in de sessie gecachete permissioncontext.

W2-000A0-provisioning is voldoende. De provisioned IDs round-trippen via de bestaande repositories en zijn rechtstreeks vergelijkbaar met de IDs in `ActiveAdministrationContext`. Er is geen nieuwe permissioncode, role, migration of repositorylookup nodig.

## Centrale authorization capability

`PermissionAuthorizer` is een kleine frameworkonafhankelijke Application-service. `allows(list<PermissionId>, PermissionId)` vergelijkt identities via `PermissionId::equals()` en retourneert uitsluitend allowed/denied. Hij queryt geen database en kent geen HTTP, Blade, Relations-code of tenantselectie.

De caller mag alleen de effective PermissionIds uit de reeds geautoriseerde actieve Administration-context aanleveren. Daardoor blijft de keten:

```text
authenticated Domain User
→ active Administration
→ valid current AdministrationMembership
→ current effective PermissionIds
→ required stable Relations PermissionId
→ allow / deny
```

Een permission uit Administration A komt niet voor in de context van Administration B en kan daar dus niet autoriseren.

## Backend routepatroon

`EnsureRelationsPermission` is het herbruikbare Presentation-middleware voor toekomstige Relations-routes. Routes gebruiken geen losse permissionstring maar de typed helper:

```php
EnsureRelationsPermission::using(RelationsPermission::View)
```

De vereiste volgorde is altijd:

1. `auth`;
2. `domain.active`;
3. `administration.active`;
4. `EnsureRelationsPermission::using(...)`.

Pas na succesvolle authenticatie, Domain User-resolutie en tenantcontext controleert het middleware de stable PermissionId met `PermissionAuthorizer`. Een geldige gebruiker zonder action permission ontvangt HTTP 403. Een ontbrekende/malforme context of onbekende permissionparameter faalt eveneens gesloten met 403. Authentication- en Administration-problemen behouden hun bestaande login- respectievelijk administration-selection-flow.

Toekomstige route mapping:

| Routehandeling | Typed definitie |
| --- | --- |
| Relations index/detail | `RelationsPermission::View` |
| Create/store | `RelationsPermission::Create` |
| Edit/update | `RelationsPermission::Update` |
| Customer-classificatiemutatie | `RelationsPermission::ClassifyCustomer` |
| Supplier-classificatiemutatie | `RelationsPermission::ClassifySupplier` |

W2-000A activeert geen businessroute en maakt geen placeholderroute in productie.

## Navigation

De dashboardcontroller gebruikt dezelfde `PermissionAuthorizer` plus `RelationsPermission::View->id()` op de requestcontext en levert uitsluitend de berekende boolean `canViewRelations` aan de layout. Blade bevat geen code, ID, rolemapping of authorizationbeslissing; het rendert alleen de vooraf berekende visibilitystate.

Met View permission toont de shell de sectie “Relaties” met één disabled item “Alle relaties”, omdat W2-001 nog geen echte route levert. Zonder View permission wordt de volledige sectie niet gerenderd. W2-001 mag het item pas activeren wanneer route én backendmiddleware bestaan. Verborgen navigatie is UX en vervangt nooit het middleware.

## Security en verificatie

- Directe URL-aanroepen zonder vereiste permission leveren 403, onafhankelijk van navigationvisibility.
- Permission IDs worden per request opnieuw uit de geselecteerde Administration geladen; role- of permissionrevocation geldt op de volgende request.
- Tenantisolatie volgt uit de combinatie UserId plus AdministrationId in de effectieve permissionquery.
- Er zijn geen permissiondatabasequeries vanuit controllers of Blade.
- Presentation bevat geen verspreide canonical permissionstrings; typed definitions zijn de enige bron.
- Een inactieve membership wordt vóór action authorization afgewezen en de actieve selection wordt gewist.
- Provisioning maakt alleen definitions en role-permission mappings; user-/membershiptoekenning blijft expliciet en buiten deze story.

Featuretests registreren uitsluitend binnen de testapplicatie geïsoleerde beschermde routes. Zij bewijzen middlewarevolgorde, 403-denial, juiste/verkeerde/meerdere permissions, cross-Administration-isolatie, next-request revocation en permission-aware navigation zonder een Relations-businessroute te introduceren.
