# W1-003C0 – OpenItem Reconstitution Contract

## Inventory and lifecycle

`OpenItem` owns immutable OpenItemId, AdministrationId, RelationId, source JournalEntryId, positive original Money and opening PostingDate. Settlement children are readonly, identity-keyed privately, and exposed in deterministic effectiveDate/ID order. `applySettlement()` validates new ID, date, positive same-Currency amount and the entire chronological balance before adding an Applied fact. `reverseSettlement()` additionally requires an existing Applied target, one reversal maximum and preserves the Applied fact.

Open amount starts at originalAmount; Applied subtracts and Reversal adds. The existing pure history calculation rejects every intermediate negative value and every value above originalAmount. `openAmountAt()` filters facts through the requested date before the same calculation. Open, PartiallySettled and Closed status are derived from the resulting Money; neither status nor open amount is independent state.

## Reconstitution contract

`OpenItem::reconstitute(...)` accepts all typed immutable basis state and a complete list of existing `OpenItemSettlement` facts. It constructs the base aggregate, sorts input by effectiveDate then settlement ID, validates and indexes children directly inside the aggregate, and runs the existing pure balance calculation. It invokes neither settlement command, emits no event, mutates no input entity and knows nothing about persistence formats.

Validation rejects duplicate child IDs, Currency mismatch, dates before opening, missing/non-Applied reversal targets, double reversal, reversal amount mismatch, and chronological balances below zero or above original. The `OpenItemSettlement` constructor continues to enforce positive amounts and Applied/Reversal reference shape. Normal creation and future commands remain unchanged after hydration.

## Verification

Focused tests cover empty state, complete immutable context, multiple Applied facts, Applied plus Reversal, unsorted input and same-date ID ordering, exact historical amounts/statuses, continued command behavior, and every listed corruption case. Existing OpenItem, OpenItemsReport and FinancialFlow behavior remains the compatibility boundary. The blocked W1-003C inventory is intentionally untouched for later resumption.
