# W1-003B – Accounting Read Persistence

## Status and inventory

**Implemented.** The earlier run stopped because a Posted `JournalEntry` could not receive hydrated lines without simulating Draft → Posted. W1-003B0 resolved this with `JournalEntry::reconstitute(...)`: all typed factual context, final enum status and children are restored at once; duplicate IDs, Currency inconsistency and invalid Posted snapshots are rejected. Hydration invokes neither `addLine()` nor `post()`, and Posted state remains immutable.

The persisted Accounting state is exactly the existing API:

- `LedgerAccount`: ID, code, name, `LedgerAccountType` and `LedgerAccountStatus`;
- `JournalEntry`: ID, AdministrationId, JournalId, PostingDate, reference and Draft/Posted status;
- `JournalEntryLine`: ID, LedgerAccountId, exactly one debit/credit Money and description;
- Money: canonical exact decimal string with at most eight fractional digits plus uppercase three-letter Currency.

No balance, report result or other derived financial value is persisted.

## Tenant ownership and schema

`LedgerAccount` intentionally remains unchanged and has no Domain `AdministrationId`. The `ledger_accounts` persistence row supplies explicit required ownership. Its globally unique ID belongs to exactly one Administration, reads always require AdministrationId, and an adapter refuses moving the same ID between tenants.

Three ordered reversible migrations add:

- `ledger_accounts`: UUID primary ID, Administration FK, factual master fields, timestamps, tenant/code uniqueness and tenant/ID candidate key;
- `journal_entries`: UUID primary ID, Administration FK, JournalId, date, reference, status, timestamps, tenant/ID candidate key and tenant/status/date/ID read index;
- `journal_entry_lines`: UUID primary ID, explicit Administration context, entry and account IDs, nullable exact debit/credit strings, Currency, description and timestamps.

Lines use composite foreign keys `(administration_id, journal_entry_id)` and `(administration_id, ledger_account_id)`. A line therefore cannot reference an entry or LedgerAccount from another Administration even when application validation is bypassed. Financial foreign keys use restrictive deletion, never cascade deletion.

## Exact Money storage

Debit and credit use nullable text columns. This deliberately preserves the Domain's arbitrary whole-number length and up to eight decimal places without DECIMAL bounds, FLOAT/DOUBLE or PHP float casts. Exactly one side is supplied by the `JournalEntryLine` invariant. Currency is stored separately as `CHAR(3)`. The adapter reads the raw amount as string and constructs `Money` directly; tests prove exact `100.12345678` roundtrip.

## Application contracts and adapters

Capability-specific ports are deliberately narrow:

- `LedgerAccountReadRepository::findForAdministration(AdministrationId)`;
- `LedgerAccountStore::save(AdministrationId, LedgerAccount)` for mutable master data with explicit ownership;
- `JournalEntryReadRepository::findPostedForAdministrationAndPeriod(AdministrationId, PostingDate, PostingDate)`;
- `JournalEntryStore::append(JournalEntry)`.

`EloquentLedgerAccountRepository` and `EloquentJournalEntryRepository` implement these contracts and are bound in `AppServiceProvider`. There is no generic repository, `findAll`, entry update or delete port.

Journal append accepts only Posted entries, rejects duplicate entry identity, validates every referenced account belongs to the entry's Administration, and inserts entry plus all lines in one database transaction. Database primary keys additionally reject duplicate line identity and the transaction rolls back the new entry. Existing financial facts are never upserted or overwritten.

The read query applies Administration, Posted status and inclusive start/end dates in SQL and orders by PostingDate then JournalEntryId. Children are loaded deterministically by line ID. Hydration constructs typed lines from exact strings and calls only `JournalEntry::reconstitute(...)`; no lifecycle transition, reflection or setter is used.

## Isolation and validation coverage

Infrastructure integration coverage proves LedgerAccount roundtrip and A/B isolation, immutable ownership, Posted entry/line/context hydration, eight-decimal Money and Currency, inclusive period bounds, Draft/before/after exclusion, deterministic ordering, duplicate entry rejection without overwrite, duplicate line rollback, adapter-level cross-tenant rejection, database-level composite tenant rejection, restrictive deletion, Posted immutability after roundtrip and service-container bindings.

No OpenItem, TaxPosting, Relations, Reporting arithmetic, dashboard or Presentation code is part of this story.
